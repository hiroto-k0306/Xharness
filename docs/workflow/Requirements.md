# Workflow 要求定義

この文書は通常の質問・作業フローの背景と目的を定義する正本です。振舞いと受入条件は [Spec](Spec.md)、構成と実現方法は [Architecture](design/Architecture.md) を参照してください。全体の要求は [製品要求](../Requirements.md)、横断的な技術・セキュリティ条件は [製品仕様](../Spec.md) に従います。

## 背景と目的

実アプリで発生した起動、コマンド実行、承認、モデル選択の失敗を、再送や権限拡張で覆い隠さず扱う必要があります。利用者が通常の会話から質問と作業を依頼し、進め方と結果、残る不確実性を一続きの会話で理解できることを目的とします。

作業を複数に分ける価値は課題によって異なります。利用者が課題に合った進め方とその理由を理解し、安全に進められる選択肢を判断できる必要があります。実行時間の短縮や品質向上を、測定のない推測で保証しません。

## ステークホルダー

| 対象             | 必要とするもの                                                         |
| ---------------- | ---------------------------------------------------------------------- |
| 作業依頼者       | 変更対象、担当モデル、承認対象、結果と残課題が分かること               |
| レビュー担当者   | 評価対象が明確で、実装者と異なる観点から妥当性を判断できること         |
| リポジトリ管理者 | 元の checkout や既存変更を無断で破壊せず、停止後の資料を確認できること |
| 保守担当者       | SDK/CLI の境界、観測したモデル、停止理由、未確認事項を追跡できること   |

## 利用者が得たい価値

- **WF-R01 会話からの作業**: 質問から作業依頼まで、専用の検証手順を意識せず目的を伝えられること。
- **WF-R02 人の判断**: 何を許可するとどのような影響があるかを理解し、自分の意思で進行や停止を選べること。
- **WF-R03 レビューと証拠**: 結果の妥当性を異なる観点から判断でき、確認した事実と未確認事項を見分けられること。
- **WF-R04 実行方法の選択**: 課題に合った進め方の理由と制約が分かり、期待と異なる方法で作業が進まないこと。
- **WF-R05 モデル選択**: 担当選択の理由と実際の利用状況を理解でき、利用できない選択肢に依存しないこと。
- **WF-R06 実績の参照**: 過去の経験を次の判断に生かしながら、難しい課題や少ない実績による偏りを避けられること。
- **WF-R07 停止の安全性**: 停止後も既存の作業と確認資料を保ち、原因と次に必要な判断を把握できること。

具体的な条件、API、実行上限、承認の振舞いと受入条件は [Spec](Spec.md) に定義します。

## 前提と非機能要求

利用者の契約・認証・作業環境を尊重した公式接続を前提とします。利用可能性、配布・OS 条件の全体要求は製品文書の対象です。機能が存在することと、利用者の環境で安全に使えることを分けて説明する必要があります。

既存のフォルダーや作業を保護し、作業方法に伴う制約と結果の確認場所を利用者が理解できることを求めます。具体的なフォルダー条件や変更の適用方法は Spec に定義します。

処理の見通し、取消、安全な停止、欠測を含む説明可能な記録を求めます。欠測や旧形式の資料が残っていても、過去の情報を保護し、新しい判断を不必要に妨げないことが必要です。保存と再開の詳細は sessions、skill 選択は skills の機能文書の責務です。

## 実装と検証の位置付け

実装状況と利用条件は Spec に定義します。mock、ローカル Git、契約テストの成功を実モデル通信や Windows の実証と読み替えません。

この文書の整理では実通信や実機検証を再実行していません。対象環境での sandbox 成立、実モデルを使った並列作業、実績参照による品質改善は未実証です。対象環境で使えることの証明は、実装があることとは別に必要です。
