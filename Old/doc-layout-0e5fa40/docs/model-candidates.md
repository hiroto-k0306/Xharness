# 品質優先のモデル候補・明示選択

現行SPEC.md §7・§10。モデルの自動最適化ではなく、固定課題で確認できる根拠・不足・枠観測を表示し、利用者が当該セッションのモデルを選ぶ最初の単位。

## 手順

1. 「改善版の比較」で比較・不変の版・課題を選ぶ。モデル／effort以外を揃えた初期状態・環境・評価条件を先に定め、同じ固定依頼を別の新規会話で測る。準備した固定依頼をコピーし、新規会話で既存ModelPickerからモデル／effortを明示選択して送信する。「新規会話で評価実行」ボタンは新規会話の通常既定値を使うため、現在のセッションに適用した候補を自動継承しない。実測の送信は利用者の明示操作だけ。開発fixtureはfake限定。
2. 出力や実行した確認の根拠を人が確認して結果登録。同じ版／課題へ複数session/taskを追記でき、同じタスクは重複登録できない。保存した結果の上書き・削除・後からの条件変更はしない。参照版の採用・復帰も、課題ごとの最新登録の有効な合格を要求する。旧ledgerを読み込めるが、反復結果を持つledgerを旧アプリへ戻して使う互換性は保証しない。
3. 「根拠付きモデル候補」→「モデル候補を確認（通信なし）」。現在のprovider実装とcatalogが対応するモデル／effortと、同じ比較・版・課題の記録だけを表示。認証・権利・endpointの稼働を実通信で確認するものではない。出典・project境界・確定履歴・固定入力・trace hashを再確認する。SKILL出典には既存の一回限りの許可、操作には既存write deny／readOnly／planの制限が適用される。
4. 品質・根拠・測定時刻・In/Out・カバー率・時間・cache内訳・scope・鮮度を確認する。模擬・不明・変更・混在構成は別表示／除外。人の明示評価は客観テスト合格と同一視しない。最新登録が有効な品質充足・全In/Out取得・全呼出の実送信記録を持つ実測の場合だけ優先検討にする。合格だけを選び出さず、不合格・模擬・欠測を含む全登録を表示する。構成・有効性を再確認できない登録がある場合は、最新構成が確定できないため当該版・課題の優先提示と数量の優劣を保留する。
5. 数量は同provider・同一cache-read/write内訳の最新有効観測同士だけで、全項目が同等以下かを理由に示す。provider間のtokenizer、異なるcache、In/Out/時間のトレードオフを単一得点にしない。同率・比較不能を残し、少数観測の統計的優越や唯一の最適とは呼ばない。枠率・トークン・料金を足し合わせず、サブスク枠をトークンから推定しない。
6. 対象を選び、理由と「モデルと根拠不足を確認して明示選択」を入力して適用。模擬・未測定・枠不明でも不足を確認した手動選択は可能。新鮮な共有枠枯渇は見送り。確認期限は取得開始から60秒までで、選択直前に根拠・枠・版・出典・選択前モデル・時刻を再確認し、変化・alias差替え・二重操作・取消を拒否する。期限切れなら候補を再取得する。
7. 当該セッションのモデル／effortを既存保存へ記録する。以前の予約・自動再開を取消し、既定値・system・ツール許可・fallback設定は変更しない。確認／選択の理由と根拠をreceipt・画面通知に残す。通信はせず、次の通常依頼が初めて通常の実行になる。保存後の取消は巻き戻しではないため、エラーや終了時は再取得して状態を確認する。

## 枠の扱いとfallback

枠の観測は現在のhome/provider接続内に保持し、account IDや資格情報を保存しない。windowごとの受信時刻・値・resetを保持し、一部windowの更新で他のwindowの時刻を新しくしない。欠けた値は古い数値で補完しない。5分以内を表示上の新鮮さとするが、provider保証や利用可能性の保証ではない。

枯渇100%以上と新鮮な429は独立pool不明として同providerの全モデルに保守的に適用する。reset到達・Retry-After到達は回復成功と同一視せず、古い／未来時刻／不明／模擬は根拠不足として表示する。再起動・認証確認／更新で観測は消し、保存した枠待ちは既存QuotaPausesが別に管理する。外部での資格情報変更をリアルタイム監視する機能や実accountのpool同定はない。

全候補が新鮮な枯渇なら選択を止め、既存「枠待ち」の条件・再開時刻・明示許可を確認するよう案内する。安全な既存checkpointがない場合は手動で待ち、勝手に再開記録やprovider試行を作らない。通常実行で429になった場合は、既存の短いRetry-After再試行と別providerへの設定済みfallbackを維持する。同ターンで429を受けたproviderの別モデルへは切り替えず、候補なしの理由をreceiptに残してrate_limitedで停止する。既存の最大3回・期限・条件照合・明示取消の再開契約を維持する。

## 限界と自動切替の条件案

現在の環境条件は申告値であり、worktree・依存・ツール構成・権限・外部状態が本当に同等かは利用者の確認が必要。本文効果だけを切り出す因果推論や反復統計、分布の安定性、cache制御、モデル品質の本番検証は行わない。候補説明は登録済み固定課題に限り、未知の依頼難度へ一般化しない。選択保存とreceipt追記の完全な一括transactionや電源断時の完全復元も今回のfake試験では証明しない。

自動切替は未採用。将来の検討には、対象課題・初期状態・構成が一致し、客観確認または明示評価の根拠が揃った複数の本番実測と失敗率、測定カバー率、分布・鮮度の基準が必要。quotaのaccount／pool／model共有範囲を実証し、欠測・古い観測・同率・全枯渇時の停止条件を定める。その上で利用者の明示opt-in、試行上限、既存fallback／再開との一貫した停止・取消、判断receiptを用意する。現状のfake結果から「自動最適」を採用しない。
