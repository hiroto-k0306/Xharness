# ユーザーが確認するプロジェクトメモリ

保存整合性・履歴検索・安全な再開を含む `c328704` の次段階。現行仕様はSPEC.md「プロジェクトメモリ」。決定 `decision`、失敗からの教訓 `failure`、手順 `recipe` を候補として残し、ユーザーが確認した内容だけを次のタスクで参照する。

## 操作

1. 登録済みプロジェクトのセッションで「履歴を確認してSQLite採用理由をメモリ候補として提案して」と依頼する。通常のモデル実行内で `SearchProjectHistory` / `ReadProjectHistory` により出典を確認し、`ProposeProjectMemory` を呼ぶ。提案ツールは既存の書き込み権限確認を通る。候補保存だけでは採用されない。
2. 「プロジェクトメモリ」で候補の内容・出典・根拠種別を確認する。「確認・編集」で本文や種類、期限を編集し「編集内容で採用」。不要なら却下。実行中は変更を受け付けない。手動候補は同じ画面から追加でき、追加後に別途採用する。手動追加・編集・採用はモデル通信を発生させない。
3. 新しい同プロジェクトセッションで `SearchProjectMemory({query:"SQLite",limit:5})` を使って参照する。通常モードでは確認欄が表示される。採用済みかつ期限・出典が有効な記録だけが通常のtool resultに返り、ツールカード・レシート・レポートで利用した本文と出典を確認できる。自動挿入やsystem接頭辞の書き換えは行わない。

提案例（出典は実在する保存済みメッセージで置き換える）:

```json
{
  "kind": "decision",
  "topic": "SQLite storage",
  "content": "ローカル単一writerの保存にSQLiteを使う。現行要件を確認してから再利用する。",
  "sources": [{ "sessionId": "past-session", "messageLine": 12 }]
}
```

`sources` は1〜3件。保存済みの当該タスクセッションも出典にできる。任意の `receiptId` を同セッションの実在toolレシートに結び付けると、ツール名と完了／エラー、ハッシュを記録する。`mergeSuggested` は同プロジェクトの統合先IDの提案だけで、既存記録を変更しない。手動候補は出典なしでも作れるが「手動記述」と表示する。

## 根拠と状態

- モデルの通常文は `model_claim`、ユーザーの通常文は `user_statement`、確認できたツールレシートは `tool_result`。ツールの完了は、その教訓全体や客観テストの合格を証明しない。本文の適否はユーザーが出典と現行コードを確認する。
- 候補の確信度は `unverified`。明示的な採用後は `user_reviewed` になり、客観テスト認証という意味は持たない。作成／更新時刻、版番号、スコープ、元メッセージのハッシュを保存する。出典の作成／更新はセッション時刻であり、メッセージ送信時刻は不明と表示する。
- 同じ種類・正規化した同じ話題の記録を、本文一致なら重複、それ以外なら矛盾の可能性として表示する。意味理解による自動判定ではない。統合はユーザーが統合先と本文を確認して確定した場合だけ。本文はユーザーの編集内容で置き換え、両者の出典を保持する。古い版からの更新は拒否して最新の再確認を求める。
- 無効化／却下／期限切れは検索対象外。無効化を編集しても再採用にはならず、新しい候補を作る。削除は記録本体をJSONから除去する。出典セッションの削除・rewind・元本文の変更・workspace忘却・receiptの消失は、記録を残して理由を表示し検索から除外する。出典を外して独立したユーザーの知識にする場合は、新しい手動候補を作って採用する。

## 境界と保存

履歴検索と同じhome／登録workspace実パス／cwd／Git common directoryの境界を使う。scratch、別project、別clone、外へ出るリンク、root自体のリンク、nested repository、別homeのSessionStoreは拒否する。自動で全プロジェクトへ展開しない。

`home/project-memory.json` は version 1、最大200件・1 MiB。既存セッション形式は変更しない。既存のhome単一writerロックに加え、同プロセスのhome単位の更新列と版番号チェックで上書きを防ぐ。既存JsonFileの同ディレクトリ一時ファイル・fsync・renameを使用し、壊れた／異なる形式は隔離して部分採用しない。書き込み失敗時は以前の完成版を維持する。旧tools hashの会話は既存の前提不一致確認に従い、互換性のために記録された接頭辞を書き換えない。

画面は同プロジェクトの更新が新しい50件を表示し、超過を明示する。古い記録を管理するには新しい不要記録を削除して再読み込みする。検索は質問200文字、候補50件、結果1〜10件（既定5）、本文1件1,200文字・合計6,000文字、出典最大3件。元履歴・レシートは1 MiBまで。全履歴の網羅検索やページ送り、semantic検索は未対応。

一覧の再取得が逆順で完了しても、後から開始した要求の結果を表示する。保存開始前の一覧応答は保存後の表示を上書きせず、保存の二重送信は画面側でも抑止する。保存整合性と版番号の照合は引き続きmain側で行う。

元本文・reasoning・画像・資格情報・レシート全文はメモリにコピーしない。本文は既存の既知秘密マスクと資格情報行／秘密鍵ブロック除外を通す。ただし未知の秘密を任意の自由文から完全識別する保証はない。機微な記録は採用せず削除する。取得結果は非信頼の参考データとして返す。昔の指示や権限を復元せず、今のpermission gateを維持する。モデルが悪意ある本文に従わないことまでmockで証明したものではない。

子エージェントは設定の `tools` に明示された `SearchProjectMemory` だけを利用でき、親のpermission gateを通る。既定子／workerの権限は拡張しない。headlessは検索のみ対応。候補提案・採用管理はデスクトップの最小機能。AGENTS.md／CLAUDE.mdの変更、グローバルメモリ、バックグラウンド抽出、追加有料モデル通信、第三者skillの取得・導入は行わない。第三者skill統合は別の将来課題。

## オフラインで再実行

```powershell
.\scripts\pnpm.ps1 test src/main/session/project-memory.test.ts src/main/session/memory-integration.test.ts src/main/tools/project-history.test.ts
.\scripts\pnpm.ps1 test
.\scripts\pnpm.ps1 typecheck
.\scripts\pnpm.ps1 lint
.\scripts\pnpm.ps1 format:check
.\scripts\pnpm.ps1 test:gui
```

GUIテストは隔離したfake homeとプロジェクトで、通常メッセージを出典に `memory-demo: <sessionId>/1` → 提案確認 → ユーザー編集・採用 → 新規タスクで `memory-search: SQLite` → 検索確認・出典表示を検証する。実Claude／Codex通信、認証CLI、サブスク枠は使わない。自動抽出や本番モデルの提案精度、Store版pwsh、パッケージ配布はこの検証の対象外。
