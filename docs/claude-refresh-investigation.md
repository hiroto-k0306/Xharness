# Claude の繰り返しログインの調査

2026-10-04。作業ブランチ: `codex/claude-refresh-investigation`。

## 依頼・許可範囲

数時間〜翌日になるとブラウザログインを求められるとの報告。
モデルに送信せず、期限切れ時に公式CLIによる更新を1回確認し、
確認できた方式へ変更することをユーザーが承認した。
自前refresh、資格情報編集・コピー、モデルへの試験送信は行わない。

## 確認したコードと記録

- `credentialStatus` と `readClaudeAccessToken` はローカル資格情報の有効期限を確認するだけで更新しない。
- `Authentication.authenticate` は期限切れと初回ログインを区別せず、
  `launchOfficialLogin` 経由で `claude auth login --claudeai` を起動する。
  このため、単なる期限切れでもブラウザログインが案内される。
  ユーザーが遭遇した各事象の原因を、通信ログで確定したわけではない。
- [Phase 5 の手元検証](phase5-local-result.md)には、期限切れ時に
  `auth status` では資格情報が変化せず、公式CLIでHaikuへ1回送信した後、
  アクセストークンが変わって有効期限内になった、と記録されている。
- [Phase 3 の記録](phase3-progress.md)も、更新時にHaikuへ1ターン送信している。
  既存の `spike:cli:refresh` はモデルへ送信するため、今回の許可では実行しない。
- [公式CLIリファレンス](https://code.claude.com/docs/en/cli-reference)は
  `auth status` を状態確認として説明する。専用の更新コマンドはこの資料では確認できない。
  `setup-token` は長期間有効なトークンを端末へ出力する別方式であり、
  現在の資格情報読み取りのみの設計にそのまま適用できるとは確認していない。

## 判断・残る作業

モデル送信なしで更新できる手順はまだ確認できていない。
「まず更新、失敗時だけログイン」の実装は、確認できた方式への変更という
承認条件を満たさないため保留。DESIGN.md §14.1の現行動作は変更しない。

既存の実測結果に沿う代替は、アプリでユーザーが許可した場合に限り、
公式CLIでHaikuへ最小リクエストを1回送り、資格情報を再読み込みする方式。
ただしサブスク枠を消費するため、今回の許可範囲外。採用には追加承認が必要。
更新失敗時だけブラウザログインを案内し、更新試行は並列起動しない。
依頼本体を自動再送せず、CLI出力をログ・IPCへ転送しない設計とする。
